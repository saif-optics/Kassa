## Правила работы
- **Дневные листы (фото).** Порядок фото обычно: 1 — Премиум, 2 — Яшнабад (если не сказано иначе).
  Сначала пересчитать каждую строку и итоги, сверить с листом, показать таблицей и
  расхождения списком вопросов. **Вносить только после команды «делай»** (или «добавляй»).
  Вопросы задавать одним сообщением, все сразу, не растягивать уточнения на несколько раундов.
  «Делаешь как всегда» = весь этот порядок.
- Если цена по частям больше записанной суммы — это скидка: скидку вычитаем из оправы
  (`price` = полная цена, `sum` = после скидки, `note` = «Чек X, оплачено Y — скидка Z»).
  «Общая скидка» — делить пропорционально по позициям чека.
- Названия расходов — как пишет владелец, не переименовывать; исправлять только цифры.
- Долги и задатки: записывать только оплаченную сумму (пропорционально по позициям),
  в `note` — «долг … не записан». Погашение долга — отдельная строка, cat «Погашения долгов»,
  product «Погашение долга … (продажа DD.MM)», note «Долг N от DD.MM …, оплачено … — долг закрыт».
  Формат строгий: блок «Долги» в разделе «Продажи» (с 10.11.2026) читает долги именно из этих пометок
  («долг N не записан» у строк чека, «(продажа DD.MM)» и «долг закрыт» у погашения).
- Доллары — пересчитать в сумы по курсу с листа, курс указать в `note`.
- Подарок — `sum` 0 и пометка («оправа в подарок»).
- Словарь листов:
  - оплата: «пеймент»/«payme» = `QR/Payme`; «хумо»/«нито»/«узкард» = `Терминал` + note «Оплата Humo/Uzcard»;
    Kaspi = `QR/Payme` + пометка; «пер» = `Перечисление`; «нал» = `Наличные`; несколько способов = `Смешанная` с `pays`;
  - товары: «з/л» = заказ линз («Линзы … (з/л)»); «стар» = Star; «сей» = Seiko; «блок» и «блю блок» = Линзы Блок (одно название, решение 11.11.2026); «ЕТ» = ET;
    «4в1» = Линзы 4в1; «с/з» = солнцезащитные; «к/л» = контактные линзы; «дет. опр» = детская оправа;
    число вроде 5501 — код оправы («Оправа 5501»). Неясный тип линз — подобрать по цене или спросить.
- Сергели: продажи приходят из Billz сами, вручную не вносить. Расходы — из журнала Excel владельца
  (линзы, доставка, мастер, месячные доставка и бонус продавца): вписывать только то, чего нет, без дублей.
- Не просить заново файлы, которые уже присылались.
- Не удалять данные без явного согласия. Секретный ключ Billz никогда не показывать в чате
  (он хранится только как секрет Supabase `BILLZ_SECRET_TOKEN`).
- Репозиторий публичный: никаких реальных данных в `dev/` и в этом файле.

## Где что лежит (таблица `public.docs`: col, id, data jsonb)
- `sales` — продажи. id `sYYp01…` / `sYYy01…` (YY — число месяца, p — Премиум, y — Яшнабад).
  С ноября 2026 — с месяцем, чтобы не совпасть с прошлыми месяцами: `sMMDDp01`, расходы `eMMDDN`, остаток `bcMMDDp`.
  Поля: point, date (YYYY-MM-DD), check, cat, product, qty, price, sum, pay
  (`Наличные` | `Терминал` | `QR/Payme` | `Смешанная` с `pays`), note, createdAt.
  Uzcard/Humo → `Терминал` + note «Оплата Uzcard/Humo». Продажи Сергели приходят из Billz сами (id `bz_…`).
- `entries` — расходы: id `eDDN`, cat `op`, type `exp`, branch = точка, source `day`.
  Остаток наличных точки за день: id `bc10DDp` / `bc10DDy`, kind/source `bc`, type `inc`,
  amount = нал − расходы (или фактически на руках, с пометкой излишка/недостачи).
- `createdAt` — реальное время в мс, **не в будущем** (иначе ломается «наличка на руках»).
- `report` — выписка р/с Анор Банка по дням: id = дата, rsStart, rsEnd, bank [{a, n, c?}].
  Из выгрузки `payments_*.xlsx`: начало дня = остаток до первой операции дня,
  конец = после последней; дебетовые операции → `bank`. Воскресенья без операций не заводим.
  rsStart дня должен равняться rsEnd предыдущего.
  Если новая выписка расходится со старой — пересобрать дни по новой.
- Billz: `bz_check`, `bz_stock`, `bz_product`, `bz_transfer`; статусы выгрузок — `docs` col `sync`.
- `fiscal/<день>` — гросс фискальных модулей по точкам {pts:{точка:{c,n,k}}}; `settings/fiscal` — привязка
  модулей к точкам (номера модулей — только в базе, не в репозитории). Источник — Rahmat (hub.rhmt.uz):
  «Отчёт по чекам» выгружается в фоне, скачивается zip с Excel (безнал — колонка «Карта»).
  В кабинет Rahmat входит сам владелец, Claude только читает и ничего там не меняет, пароли не вводит.
  Раздел на сайте выключен, пока владелец не скажет включить.

## Распределение работы (экономия токенов) — решение владельца 06.11.2026
Главная сессия — **Fable, надзиратель**. Сама делает только то, что нельзя отдать: разговор с владельцем, чтение
фото листов, решения по деньгам, запись в базу, коммит и push. Всё остальное — задание исполнителю, а Fable
проверяет результат. Порядок любой задачи (решение владельца 17.11.2026): сначала вопросы для понимания, затем карта работ по пунктам на его комментарии,
итог, и только после команды «делай» — правки. Порядок любой задачи с кодом:
1. **Разведка** — `kassa-scout` (Haiku) находит место в коде; `kassa-sql` (Haiku) — проверочные SELECT.
2. **Исполнение** — `kassa-dev` (Sonnet) правит код по заданию (web/ или dev/), сам гоняет tsc/сборку и сверку
   раздела, отчитывается. Разборы месяца, себестоимость, Excel — `kassa-analyst` (Sonnet), только чтение базы.
   Независимые куски — разным исполнителям параллельно, но два исполнителя не правят одни файлы.
3. **Проверка** — `kassa-build` (Haiku) собирает всё и прогоняет тесты, сверки и скриншоты;
   `kassa-review` (Sonnet) смотрит diff на ошибки в логике и деньгах.
4. **Стресс-тест** (с 17.11.2026, по решению владельца): перед приёмкой любой новой функции — попытки обхода и предельные случаи
   (чужие данные, лишние поля, лимиты сумм/дат/длины, огромные записи, повторы, пустые права) через SQL с подменой пользователя
   в транзакции с откатом и через `dev/test/t_stress.py` (большие данные, время входа и отрисовки, ошибки консоли; `build.ps1 -Stress`).
   Найденное закрывается до коммита, результаты коротко в отчёт владельцу.
5. **Приёмка — сама Fable**: читает отчёты, смотрит ключевые места diff и скриншоты, при сомнении повторяет
   проверку. Только после чистых сборки, сверок и ревью — коммит; push и выкладка — только по команде владельца.
Задание исполнителю: что и где менять, как проверить, чего не трогать; без пересказа всей переписки.
Не отдавать исполнителям: запись в базу, git commit/push, сообщения от имени владельца, решения по деньгам.
Мелочь (один запрос, правка до 10 строк) — делать самой: запуск помощника тоже стоит токенов.
Новая версия (web/): проверки = `npx tsc -b`, `npm run build`, сверки `web/scripts/*-parity.ts`, скриншоты
`web/scripts/shots.py` при запущенном сервере 5173 (launch.json «kassa-web»). Node: `C:\Users\user\.local\node`.
Сборка на Windows: `powershell -File dev\build.ps1 -Test`.
Выкладка серверной функции: правка `supabase/functions/<имя>/index.ts`, затем `powershell -File dev\deploy-fn.ps1 <имя>`
(Supabase CLI в `~/.local/supabase`, вход один раз `supabase login`). Не передавать код функции целиком через MCP — это дорого.

## Карта кода (Graphify)
В `graphify-out/` лежит граф кода: функции, файлы и связи между ними (`graph.json`, обзор — `GRAPH_REPORT.md`,
картинка — `graph.html`). Graphify ставится сам при старте сессии (хук в `.claude/settings.json`);
если нет — `pip install graphifyy==0.9.97`.
- Прежде чем искать по коду (grep, чтение файлов), спросить граф: `graphify query "<вопрос>"`,
  связь двух вещей — `graphify path "<A>" "<B>"`, одна функция — `graphify explain "<имя>"`,
  что заденет правка — `graphify affected "<имя>"`. Потом читать только найденные строки.
- Код `dev/base.html` попадает в граф через зеркало `dev/graph-src/base.html.js`: **номера строк в нём
  совпадают с base.html**. Править всегда `base.html`, зеркало не трогать — оно пересоздаётся.
- `bash dev/build.sh` сам обновляет зеркало и граф (без LLM, бесплатно). Изменения в `graphify-out/`
  коммитить вместе с кодом; большой diff `graph.json` — это нормально.

## Роли доступа (с 16.11.2026, права-переключатели с 17.11.2026)
Таблица `public.members(email lower, role, point, label, phone, "position", note, perms jsonb, active)`.
- Вход — Supabase Auth; строка в `members` даёт статус, точку и права (RPC `my_access` → role, point, perms, label). `active=false` снимает доступ.
  Пользователей заводит владелец (или админ) на сайте во вкладке «Пользователи» через серверную функцию `users-admin`
  (service role только внутри Supabase). Пароли в репозиторий, чат-итоги и память не писать.
- Статусы: **owner** (владелец, одна запись — его почта; триггер `members_guard` не даёт удалить, выключить или понизить) →
  **admin** (всё, кроме владельца и других админов) → **cashier**, **seller**, **marketer** («Гость»). Владелец и админ читают таблицы
  напрямую по RLS (`is_admin()`), точка у них может быть «Все точки» (null). У остальных ровно одна точка.
- Права (ключи `perms`): `sales_view, sales_write, sales_edit, exp_view, exp_add, exp_edit, cash_view, debts_view, att_view, analytics, export`.
  Набор по умолчанию задаёт статус (`role_perms(role)`): cashier — всё кроме analytics/export; seller — sales_view, exp_view, exp_add, att_view;
  marketer — sales_view, analytics. `members.perms` — переопределения владельца (итог = по умолчанию || perms). Вкладки и кнопки на сайте
  идут по правам: «Продажи» (sales_view), «Аналитика» (analytics), «Приход» (att_view).
- Ограниченные роли читают данные одним вызовом `role_docs_all()` (продажи без `cost/costEst/costSrc/photo`, `settings/sales` без плана,
  расходы только `source=day`; точка фильтруется, если задана) и пишут только через RPC: `cashier_put_sale`/`cashier_del_sale`
  (sales_write/sales_edit: своя точка, сегодня/вчера, белый список полей, продажа до 500 000 000, Billz не трогает, себестоимость
  старой строки сервер сохраняет), `cashier_put_entry`/`cashier_del_entry` (exp_add/exp_edit: `cat=op`, до 50 000 000, только `source=day`),
  `seller_add_expense` (exp_add без exp_edit: шаблоны `settings/sellerTpl`, до 3 000 000, до 30 в день, дата не старше позавчера),
  `att_my_load` (att_view, журнал прихода своей точки без кодов и фото). Realtime для них не подписывается.
  Не видят никогда: себестоимость, прибыль, план, р/с, платежи, фискальные модули, Billz, склад, настройки, чужие точки.
- Функции Billz (`billz-sync`, `billz-collect`) вручную запускает только активный owner/admin.
- SQL — `supabase/migrations/2026111*_roles*.sql` (по порядку номеров), сервер — `supabase/functions/users-admin`,
  клиент — `dev/patch_role.py` + `dev/role/` (`users.js` — панель пользователей), тест — `dev/test/t_role.py`.
